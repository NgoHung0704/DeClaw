## Locked architectural decisions
- Python 3.12+ with uv (lockfile committed)
- LangGraph for agentic loop
- Ollama + Mistral 7B Instruct (default); nomic-embed-text for embeddings
- Docker sandbox **mandatory** for shell execution (disabled, never bypassed, when Docker unavailable)
- Dual-model sanitizer (second Mistral instance, locked prompt) for prompt injection defense
- ChromaDB for vector memory (Fernet at-rest encryption)
- FastAPI gateway binds `127.0.0.1:7842` only
- python-keyring for credentials (NO plaintext anywhere)
- **Plugin-first architecture** — every capability is a plugin in its own subprocess
- ed25519 signatures required for third-party plugins
- Tauri 2.0 desktop shell (Windows first, then macOS, Linux)
- Frontend: Vanilla JS + TailwindCSS CDN (zero build step), EN + FR i18n
- AGPL-3.0 license (commercial dual-license possible later)

## The 7 Inviolable Principles
1. NEVER store credentials in plaintext — always python-keyring
2. NEVER bind the gateway outside `127.0.0.1` — no LAN, no `0.0.0.0`
3. NEVER execute shell commands outside the Docker sandbox — if Docker is unavailable, the tool is **disabled**, not bypassed
4. NEVER skip the sanitizer layer on content sourced from outside the agent (email, web, file contents from user-pointed folders)
5. NEVER auto-trust content from documents/emails/web — treat as potentially adversarial
6. NEVER let an LLM call a function with raw user input as a shell string — all tools take **typed, validated parameters**
7. NEVER make a network call without logging it to the audit trail — "data left the device" must be observable

## Target market (MVP v0.1)
EU regulated professionals — lawyers, notaries, doctors, accountants — who cannot legally use cloud AI due to GDPR + professional secrecy. France-first.

## MVP definition of done
1. Install in < 5 min, no terminal required
2. Point at folder of PDFs/DOCX/XLSX
3. Ask in French or English, get cited answers
4. Move/rename/summarize via natural language (with confirmation)
5. Audit log shows what happened, in natural language
6. Network egress monitor confirms nothing left the device

### Phase 1 — Core Brain
- **DCL-016** — CLI test interface. `declaw/brain/repl.py` adds `build_brain(tools=None)` — the first end-to-end assembly: `build_agent_graph(model=with_context_window(with_tool_call_repair(build_ollama_model(tools), tools)), tools)` (default tools `[echo]`; compaction composes too but is left off by default) — and `run_chat(graph, *, read, write, debug=False)`, a multi-turn REPL whose I/O is injected so it is testable without a terminal or daemon (`/exit`/`/quit` to stop, blank lines skipped, `--debug` prints `[tool call]`/`[tool result]` lines, `_reply_text` returns the latest assistant message with visible text). `declaw chat` (`declaw/main.py`) now health-checks Ollama (reachable + model pulled, else an actionable exit), builds the brain, and drives the REPL via `console.input`/`console.print` (lazy import keeps `version`/`status` light; ASCII banner avoids Windows mojibake). 5 unit tests in `tests/unit/test_repl.py` (build_brain smoke, multi-turn memory, exit, blank-skip, debug rendering) + 1 self-skipping integration test in `tests/integration/test_chat_repl.py` running one real turn through live Mistral. Verified live on dev hardware.
- **DCL-015** — Context compaction strategy on overflow. `declaw/brain/compaction.py` upgrades DCL-014's plain eviction: once a token `threshold` is crossed, the oldest turns are replaced by a single `SystemMessage` summary note instead of being dropped, while a leading `SystemMessage` and the `keep_recent` most recent turns are kept verbatim (a leading orphan `ToolMessage` in the tail is dropped). `compact_messages(messages, *, summarize, threshold, keep_recent, counter)` is the async core (no-op under threshold or when nothing is older than `keep_recent`); `make_summarizer(model)` builds the default `Summarizer` from a `ModelCallable` (prompt: concise summary, preserve facts/decisions/plan, no tool calls); `with_compaction(model, ...)` is the composable `ModelCallable` wrapper. Like DCL-014 it trims the model-facing view only (full history stays in `AgentState`); the task plan is preserved by living in the `AgentState.plan` slot rather than in messages. Defaults reuse DCL-014's `estimate_tokens` + `DEFAULT_SOFT_CAP`, `keep_recent=6`. 7 unit tests in `tests/unit/test_compaction.py` use a fake summariser + injected counter (no-op under threshold, fold oldest into a note, preserve system, nothing-old no-op, orphan-tool drop, default-summariser content, wrapper triggers compaction then returns the reply). Persisting the summary into state to avoid per-turn re-summarisation is a later optimisation.
- **DCL-014** — Context window management (Mistral 32k). `declaw/brain/context.py` keeps the prompt under the model's window by trimming the *model-facing* message view (the full history stays in `AgentState` for audit). `estimate_tokens` is a conservative heuristic (~ceil(chars/3) + per-message overhead — over-estimates so we never silently exceed); a precise tokenizer can be injected via the `TokenCounter` seam. `fit_to_window(messages, *, hard_cap, soft_cap, counter)` is a no-op under `hard_cap`, else evicts oldest messages down to `soft_cap` (so it doesn't trim every turn), always keeping a leading `SystemMessage` + the most recent message, and dropping a leading orphan `ToolMessage`. `with_context_window(model, ...)` is a composable `ModelCallable` wrapper (stacks with `with_tool_call_repair`). Defaults: hard=30720 (32768−2048 response reserve), soft=24000. 8 unit tests in `tests/unit/test_context.py` cover counting, eviction/preservation rules with an injected counter, the wrapper trimming before the model sees messages, and a real-`estimate_tokens` long conversation staying ≤ hard cap. Eviction = plain drop; summarising evicted turns is DCL-015.
- **DCL-013** — Tool output parser + retry/repair. `declaw/brain/repair.py` provides `with_tool_call_repair(model, tools, *, max_retries=2) -> ModelCallable`, a composable decorator around a `ModelCallable`: it inspects each reply for bad tool calls and, if any, re-prompts the model with a corrective message (max 2 retries) before returning the last attempt unchanged (so the loop never hangs — `ToolNode` surfaces any residual error). `_tool_call_problems` detects three failure modes: `invalid_tool_calls` (args not valid JSON), unknown tool name, and args that fail the tool's pydantic `args_schema` (missing/invalid params). Standalone by design (compose as `with_tool_call_repair(build_ollama_model(tools), tools)`; DCL-016 wires it in). 7 unit tests in `tests/unit/test_repair.py` use a scripted model over a small corpus of malformed outputs: each failure mode repairs to a valid call after one retry, persistent malformation gives up after `max_retries` (1 + max_retries calls), valid/plain replies skip retry, and the corrective prompt is verified to be sent. No integration test (acceptance is a deterministic corpus; provoking a 7B to misbehave reliably is flaky).
- **DCL-012** — Ollama function calling integration. `declaw/brain/chat_model.py` provides `build_ollama_model(tools, *, model=None, base_url=None) -> ModelCallable` — it constructs `langchain_ollama.ChatOllama` (model/base_url default to Settings), calls `.bind_tools(tools)` so Mistral knows the tool schemas, and returns an async adapter `messages -> await bound.ainvoke(messages)`. This fills the injected `ModelCallable` seam from DCL-010, so the same `build_agent_graph` now runs on a real model; the bound tools must match the executor tools passed to `build_agent_graph`. 2 unit tests in `tests/unit/test_chat_model.py` fake `ChatOllama` at its construction boundary (no daemon): one asserts the factory wires Settings + binds the tool and returns a tool-calling `AIMessage`; the other plugs the built model into `build_agent_graph` and proves a structured tool call routes to the executor (echo runs, then the model answers). 1 integration test in `tests/integration/test_ollama_function_calling.py` self-skips unless Ollama is reachable with the model pulled, then round-trips the real Mistral through `bind_tools` and asserts an `AIMessage` returns (soft-checks any tool_calls are well-formed echo calls; hard tool-call reliability is DCL-013). Verified live on dev hardware (Mistral 7B reachable).
- **DCL-011** — AgentState schema with typed slots. `declaw/brain/state.py` defines `AgentState`, a Pydantic `BaseModel` used as the LangGraph state schema — it replaces the placeholder `MessagesState` from DCL-010 and is now wired into `build_agent_graph`. Five slots: `messages` (`Annotated[list[AnyMessage], add_messages]` — the only reducer field, so it appends rather than overwrites; `AnyMessage` is a discriminated union, so message subclasses survive JSON round-trips), `scratchpad` (str), `plan` (`list[str]`), `tool_calls` (`list[ToolCall]`), `audit_refs` (`list[str]`, for Principle #7). Being a `BaseModel`, it serializes via `model_dump_json()`/`model_validate_json()`. The loop's `think` node now reads `state.messages` (attribute) instead of `state["messages"]`; `ainvoke` still returns a plain dict, so callers/tests are unchanged. 2 unit tests in `tests/unit/test_state.py` cover empty defaults and a full serialize→deserialize round-trip (4 mixed messages + populated slots, asserting subclass preservation and `restored == state`). Planning/audit slots are defined now; later tickets populate them.
- **DCL-010** — LangGraph basic agentic loop. `declaw/brain/loop.py` exposes `build_agent_graph(model, tools)`: a two-node LangGraph state machine implementing think → tool-call → observe — an `agent` node (calls the injected async model) and a `tools` node (`ToolNode` runs requested tools). `tools_condition` loops back to `agent` while the model emits `tool_calls`, else routes to `END`. State is LangGraph's `MessagesState` (DCL-011 will extend it). The model is **injected** as an async `ModelCallable` (`Sequence[BaseMessage] -> Awaitable[BaseMessage]`) so the loop is testable with no live Ollama — real Mistral wiring via langchain-ollama `bind_tools` is DCL-012. `declaw/brain/stub_tools.py` ships an `echo` stub tool (real typed tools arrive in Phase 2 / DCL-020+). 2 unit tests in `tests/unit/test_loop.py` drive the loop with a scripted fake model: one proves the full `Human → AI(tool_call) → Tool → AI(answer)` trace with the stub tool, the other proves the no-tool-call path ends after a single think. mypy-strict gotchas: `CompiledStateGraph` takes 4 type params; the model param must be `Sequence` (list is invariant); the agent node must be an inline `async def` for mypy to infer `NodeInputT`.

## Open decisions
- **Ollama lifecycle / end-user packaging** (raised 2026-05-27). MVP DoD requires "install in < 5 min, no terminal required" for non-technical users (lawyers, doctors). They cannot manually install Ollama, pull a model, or fix PATH — yet that is exactly the current dev setup. DeClaw must own the full Ollama lifecycle (install, start daemon, health-check, auto-pull missing model) and hide it from the user, surfacing only a "preparing AI engine…" progress UI. Options:
  - **A — Bundle Ollama** inside the Tauri installer (heavier app ~hundreds of MB, must track Ollama versions).
  - **B — Download on first run** (light installer, needs internet once for ~4GB model; must log the download to the audit trail per Principle #7 and clearly frame it as "one-time, then fully offline").
  - **C — Embed llama.cpp/llamafile directly** (drop Ollama; full control but lose Ollama's model management + API, more work).
  - End-user config (`ollama_base_url`, `model`) must default to sane values (run with zero config) and be changed only via the Phase 9 Settings UI — never via `.env`/terminal. **Likely needs a dedicated ticket** ("Ollama lifecycle management") around Phase 7 or earlier. Decision deferred — no option chosen yet.
- **Docker requirement for end-users / shell execution in MVP** (raised 2026-05-27). Per Principle #3, Docker is mandatory *only for shell execution* — "disabled, not bypassed" when absent. So Docker's absence must **disable the shell tool, not block the app**. Key realization: **the v0.1 MVP feature set does not need shell execution.** The 5 DoD items (read PDF/DOCX/XLSX, cited Q&A, move/rename/summarize via NL, audit log, egress monitor) all work without a shell — file move/rename runs through the os-bridge plugin with **typed, validated parameters** (Principle #6) via Python `shutil`, not shell commands. Meanwhile Docker Desktop is a *heavier* burden on non-technical users than Ollama: (a) needs WSL2 + BIOS virtualization + admin rights, which lawyers/doctors typically can't set up; (b) **Docker Desktop licensing is paid** for orgs >250 employees OR >$10M revenue — law firms / medical practices may fall under this, a real cost/legal risk; (c) multi-GB RAM footprint. Options:
  - **A — Drop shell execution from v0.1** (recommended leaning): no Docker dependency at all for MVP → lightweight install, matches "< 5 min, no terminal". Shell + sandbox deferred to post-MVP.
  - **B — Keep shell in v0.1** but solve the sandbox-for-non-technical-user problem without forcing Docker Desktop: candidates are Windows Sandbox (Win Pro built-in), WSL2 directly (avoids Desktop licensing), gVisor/Firecracker/nsjail (Linux-first), or bundling Docker Engine (not Desktop).
  - Two follow-ups regardless of choice: (1) the **end-user runtime startup** must treat a failed Docker check as "disable shell tool + warn", unlike the current dev `scripts/preflight.py` which exits 1 — `declaw/preflight.py` does not yet distinguish these two modes. (2) **Phase-gating impact**: Phase 3 (sandbox) is currently a gate for Phase 9 (Web UI); if shell is deferred, Phase 3 may drop off the MVP critical path (Phase 4 sanitizer remains the real gate) — revisit gating separately. Decision deferred — no option chosen yet.
- **Proactive "heartbeat" agent loop (OpenClaw-style)** (raised 2026-05-28). OpenClaw (Peter Steinberger's self-hosted local AI assistant — close in philosophy to DeClaw) has a *heartbeat*: on a fixed interval (~30 min) the system wakes the agent, which reads a `HEARTBEAT.md`, performs configured checks (email, calendar, metrics), and either reports or stays silent (`HEARTBEAT_OK`, <1k tokens). This turns a **reactive** agent (waits for commands) into a **proactive** one (acts on a schedule). DeClaw is currently reactive-only, but the roadmap already has the foundation: **APScheduler** (listed under Future ideas, Phase 2 / post-MVP). Reasoning on whether DeClaw should adopt this:
  - **For**: genuinely useful for the target professionals (watch a folder for new docs, remind about deadlines, summarize newly-arrived email); a differentiator vs purely reactive assistants; scheduler infra already planned.
  - **Against (tensions with DeClaw's DNA)**: (1) conflicts with the **confirmation-required** model (MVP DoD #4) — who confirms an autonomous action when the user is away? (2) **legal-liability risk** for regulated professionals — an agent auto-acting on privileged email without supervision is dangerous; (3) **privacy/audit** — scheduled access to email/calendar even when the user is absent must be fully local + logged (Principles #5, #7); (4) **LLM reliability** — DeClaw runs local Mistral 7B, far weaker than the cloud models OpenClaw likely assumes; autonomous decisions on a 7B model are risky; (5) cost is compute/electricity on the user's machine (not API $, since Ollama is local).
  - **Leaning**: keep DeClaw **reactive for v0.1**; treat proactive heartbeat as **post-MVP**, built on APScheduler. Even then, default to **"observe + notify"** (watch and surface findings), **not "act autonomously"** — any action still routes through the confirmation queue + audit trail. Decision deferred — no option chosen yet.
- **User-behavior / preference memory gap** (raised 2026-05-28). Standard agent-memory taxonomy has 4 types: short-term (working/conversation buffer), semantic (facts + **user-specific** preferences/profile/prior decisions), episodic (timestamped log of past interactions), procedural (learned how-to/workflows). DeClaw's Phase 5 covers: DCL-052 short-term buffer ✓, DCL-053 semantic (but scoped "vector search by **topic**" — document-oriented, NOT user preferences), DCL-054 episodic (task history), DCL-055 retrieval-into-context. **Gap**: no ticket builds a *user-preference / behavioral* memory layer (preferred language, answer style, frequent folders/actions), and **no procedural memory** ticket at all. So DeClaw has the infrastructure (ChromaDB + nomic-embed-text + episodic store) to remember user behavior, but the current plan does not explicitly *learn* preferences to improve UX. Notably DeClaw is **well-positioned to do this ethically** vs cloud assistants: 100% local, Fernet at-rest (DCL-051), GDPR export (DCL-056) + wipe (DCL-057), audit trail — could be a privacy-first differentiator ("learns your habits, 100% on-device, erasable anytime"). Caveats: for regulated professionals this is sensitive profiling → must be **opt-in + transparent + wipe-able**; procedural automation must still route actions through confirmation (same tension as the heartbeat decision). Possible follow-up tickets (Phase 5 or post-MVP): (1) "User preference memory" — a semantic sub-collection for stable profile facts; (2) "Procedural memory" (post-MVP) — learn repeated workflows. Decision deferred — no ticket added yet.
