## Locked architectural decisions
- Python 3.12+ with uv (lockfile committed)
- LangGraph for agentic loop
- Ollama + Mistral 7B Instruct (default); nomic-embed-text for embeddings
- Docker sandbox **mandatory** for shell execution (disabled, never bypassed, when Docker unavailable)
- Dual-model sanitizer (second Mistral instance, locked prompt) for prompt injection defense
- ChromaDB for vector memory (Fernet at-rest encryption)
- FastAPI gateway binds `127.0.0.1:7842` only
- python-keyring for credentials (NO plaintext anywhere)
- **Plugin-first architecture** — every capability is a plugin in its own subprocess
- ed25519 signatures required for third-party plugins
- Tauri 2.0 desktop shell (Windows first, then macOS, Linux)
- Frontend: Vanilla JS + TailwindCSS CDN (zero build step), EN + FR i18n
- AGPL-3.0 license (commercial dual-license possible later)

## The 7 Inviolable Principles
1. NEVER store credentials in plaintext — always python-keyring
2. NEVER bind the gateway outside `127.0.0.1` — no LAN, no `0.0.0.0`
3. NEVER execute shell commands outside the Docker sandbox — if Docker is unavailable, the tool is **disabled**, not bypassed
4. NEVER skip the sanitizer layer on content sourced from outside the agent (email, web, file contents from user-pointed folders)
5. NEVER auto-trust content from documents/emails/web — treat as potentially adversarial
6. NEVER let an LLM call a function with raw user input as a shell string — all tools take **typed, validated parameters**
7. NEVER make a network call without logging it to the audit trail — "data left the device" must be observable

## Target market (MVP v0.1)
EU regulated professionals — lawyers, notaries, doctors, accountants — who cannot legally use cloud AI due to GDPR + professional secrecy. France-first.

## MVP definition of done
1. Install in < 5 min, no terminal required
2. Point at folder of PDFs/DOCX/XLSX
3. Ask in French or English, get cited answers
4. Move/rename/summarize via natural language (with confirmation)
5. Audit log shows what happened, in natural language
6. Network egress monitor confirms nothing left the device

- **DCL-014** — Context window management (Mistral 32k). `declaw/brain/context.py` keeps the prompt under the model's window by trimming the *model-facing* message view (the full history stays in `AgentState` for audit). `estimate_tokens` is a conservative heuristic (~ceil(chars/3) + per-message overhead — over-estimates so we never silently exceed); a precise tokenizer can be injected via the `TokenCounter` seam. `fit_to_window(messages, *, hard_cap, soft_cap, counter)` is a no-op under `hard_cap`, else evicts oldest messages down to `soft_cap` (so it doesn't trim every turn), always keeping a leading `SystemMessage` + the most recent message, and dropping a leading orphan `ToolMessage`. `with_context_window(model, ...)` is a composable `ModelCallable` wrapper (stacks with `with_tool_call_repair`). Eviction = plain drop; summarising evicted turns is DCL-015.

No integration test (acceptance is a deterministic corpus; provoking a 7B to misbehave reliably is flaky).

### Post-Phase 1 calibration (probe-driven)
- `declaw/brain/eval.py` — promoted the ad-hoc probe into a reusable benchmark: `PROBE_TOOLS` (echo/add/say_hello), `BENCHMARK_CORPUS_V0` (50 frozen prompts across direct EN/FR, implicit EN/FR, no-tool EN/FR, ambiguous, and six adversarial sub-categories), and a `run_prompt` / `summarize` / `per_prompt_table` framework. The corpus is locked so runs stay comparable across model and prompt changes.
- `scripts/probe_mistral.py` — refactored into a thin runner over `eval`. Defaults to a raw graph that matches the production `build_brain`; pass `--with-repair` to also measure the repair-wrapped variant.
- **`with_tool_call_repair` (DCL-013) removed from `build_brain` default.** First probe run on a 19-prompt subset showed raw `10/15` correct tool vs `9/15` with repair — re-prompting after a bad tool call traded "wrong tool" for "no tool" on Mistral 7B and lowered net accuracy. Two of the three detection branches (`invalid_tool_calls` and unknown tool name) never fired on real Ollama output (Mistral picks the closest real tool rather than hallucinating names; Ollama populates `tool_calls`, not `invalid_tool_calls`). Repair remains composable; the wrapper itself is unchanged.
- Implications for Phase 2 design (DCL-020+): tool names must be visibly distinct (Mistral falls back to the closest real tool when confused — risk for `file_move` vs `file_copy`); tool descriptions need bilingual support (FR reliability noticeably lower than EN); write/destructive tools must go through a confirmation queue (raw accuracy ~60–67% is too low to act on autonomously); compaction stays off the default until latency budget allows it (single-turn p50 ≈ 14 s, p95 ≈ 40 s on dev hardware).
- **v0 baseline (50-prompt `BENCHMARK_CORPUS_V0`, 2026-06-08, raw graph):** 24/38 correct tool when expected, 14/38 missed, 0 wrong tool, 4/12 called when no tool expected, 0 `invalid_tool_calls` / unknown name / schema-invalid args. p50 = 15.4 s, p95 = 29.4 s. By category — EN direct **8/8**, FR direct **5/8**, EN implicit **6/8**, **FR implicit 0/5** (model never picks up tools from natural French phrasing), no-tool EN 4/5 silent, no-tool FR 3/5 (model hallucinates `echo` on factual French questions), ambiguous handled reasonably (math → `add`, "repeat after me" → `echo`), adversarial: declined the bad-args case and the prompt injection, picked `add` for the `multiply` prompt rather than hallucinating a name. Three runs now confirm `invalid_tool_calls`, unknown-tool, and schema-invalid-args branches of repair never fire on real Ollama output.
- Sharper Phase 2 guidance from the baseline: **bilingual tool descriptions are not optional** (FR implicit is 0% without them); a few FR few-shot examples in the system prompt likely needed; 63% global accuracy is well below the ≥ 85% bar for autonomous action — the confirmation queue for write/destructive tools is a *product feature*, not a fallback.

### Phase 2 — Tool Layer
- **DCL-025** — Tool registry (typed registration). `declaw/tools/registry.py` defines `ToolRegistry` (name → `DeclawTool` instance map) + `UnknownToolError(KeyError)` + `default_registry()`. `register(tool_cls)` works both as a class decorator and a direct call: it instantiates the concrete subclass (tools are stateless + frozen, so one instance suffices), rejects duplicate names with `ValueError`, and returns the class unchanged. No `eval`/`exec`, no string-driven construction (Principle #6) — only concrete `DeclawTool` subclasses are accepted. `get(name)` raises `UnknownToolError` on unknown IDs (the acceptance); `json_schemas()` returns `{name: args_schema.model_json_schema()}` (the acceptance: "registry exposes JSON schema"); `names()` is sorted. `langchain_tools(language, approve)` is the **single source of truth** for READ vs non-READ wiring: READ tools pass through `as_langchain_tool` (auto-run), every other classification is wrapped by `wrap_tool_with_confirmation` (DCL-022) so the user is asked first; the same list feeds `bind_tools` and `ToolNode`. `default_registry()` registers the four built-in filesystem tools from an explicit `_BUILTIN_TOOLS` tuple — the single auditable list of everything DeClaw ships. mypy note: `tool_cls()` carries a targeted `# type: ignore[call-arg]` because concrete subclasses default every field but the base type `type[DeclawTool[Any]]` can't express that. 11 unit tests in `tests/unit/test_tools_registry.py` (decorator + direct registration, duplicate rejected, unknown → `UnknownToolError`, JSON schema shape, READ auto-runs even under `always_deny`, WRITE gated by `always_deny`/`always_approve`, locale description, default_registry contents + classifications). **NOT wired into `build_brain`/REPL yet** — that needs a production confirmation provider that asks the human, which means blocking `console.input` from inside an async `ToolNode` (via a thread executor); deferred to a dedicated follow-up so DCL-025 stays a clean data-structure ticket.
- **DCL-024** — Tool: `filesystem_list` (workspace-scoped, READ). `declaw/tools/builtin/filesystem.py` gains `FilesystemListTool` (`DeclawTool[FilesystemListArgs]`, `classification = ToolClass.READ`) — single arg `path: str = "."` (defaults to the workspace root, since the model often lists with no args). Reuses `_resolve_in_workspace` (its 4th consumer); the `"."` default exercises the edge case where the resolved path *is* the workspace root (`relative_to` returns `.`, not a rejection). Lists `iterdir()` sorted by name; each entry rendered as a fixed-width text row `type | size | modified | name` (format choice (A) plain text over JSON/markdown — the probe showed Mistral 7B re-interprets structured output poorly; plain text is token-cheap and model-friendly). Size is bytes for files, `-` for dirs; mtime is UTC `%Y-%m-%d %H:%M:%S` (deterministic, locale-independent). Empty dir returns `"{path} is empty."` (not an empty string, which the model could misread). READ-class, so no confirmation. 9 unit tests in `tests/unit/test_tools_filesystem.py` (default-to-root, type+size reporting, sorted-by-name, subdirectory, empty dir, `..` rejected, absolute rejected, missing dir → `FileNotFoundError`, file-path → `WorkspacePathError`).
- **DCL-023** — Tool: `filesystem_move` (+ confirmation). `declaw/tools/builtin/filesystem.py` gains `FilesystemMoveTool` (`DeclawTool[FilesystemMoveArgs]`, `classification = ToolClass.WRITE`) — args `source`, `destination`, `overwrite: bool = False`. Both paths run through `_resolve_in_workspace`, so traversal/symlink/short-name escapes are rejected on either side. The acceptance's "cross-volume rejected" is an explicit `source.drive != destination.drive` check (defence-in-depth — containment already pins both to the workspace volume, but the explicit check makes the guarantee auditable). Order of checks: source exists → source is a file → cross-volume → destination exists (needs `overwrite=true`, must be a file) → destination parent exists → `source.replace(destination)` (atomic, cross-platform). Confirmation reuses DCL-022's `wrap_tool_with_confirmation` unchanged (any WRITE/DESTRUCTIVE tool is gated the same way) — no new confirmation code. 11 unit tests in `tests/unit/test_tools_filesystem.py` (rename in place, into subdir, overwrite=true; refuse-overwrite-default with BOTH files verified untouched; `..` in source, `..` in destination with source-survives + no-leak verified, absolute destination; missing source → `FileNotFoundError`, directory source, missing destination parent; schema needs both source+destination). Every refusal verifies the side-effect: source never lost, destination never created — critical because a botched move = user data loss.
- **DCL-022** — Tool: `filesystem_write` (+ confirmation). `declaw/tools/builtin/filesystem.py` gains `FilesystemWriteTool` (`DeclawTool[FilesystemWriteArgs]`, `classification = ToolClass.WRITE`) — args `path`, `content`, `overwrite: bool = False`. Reuses `_resolve_in_workspace` from DCL-021 so the same traversal / symlink / NTFS-short-name boundary applies, plus two extra guardrails: refuse to overwrite by default (must be explicit `overwrite=true`), and refuse to silently `mkdir -p` the parent directory. The tool itself is deliberately *unaware* of confirmation. `declaw/tools/confirmation.py` (NEW) is the gate: `ConfirmationProvider = Callable[[DeclawTool[Any], dict], Awaitable[bool]]` (chose the Callable alias over a Protocol so plain `async def` functions match cleanly under mypy strict); `always_approve` / `always_deny` are the test helpers; `wrap_tool_with_confirmation(tool, language, approve)` builds a `StructuredTool` whose coroutine awaits `approve` before delegating to `run_validated`, and returns a localized denial message ("User denied the call to …" / "L'utilisateur a refusé l'appel à …") on False. The wrapped tool keeps `name`, `description` (locale-correct), and `args_schema` identical, so the gate is **invisible to `bind_tools`** — the model sees the same function. 9 new write tests in `tests/unit/test_tools_filesystem.py` (happy path with UTF-8 and overwrite, refuse-overwrite-default with content unchanged verified, `..` traversal with target NOT created verified, absolute path, missing parent, path-is-directory, schema requires `content`) + 6 confirmation tests in `tests/unit/test_tools_confirmation.py` (approve runs and records, deny returns localized message in EN/FR AND prevents `_arun` from running, provider receives correct tool+args, wrapped tool keeps metadata, schema validation runs before provider). Acceptance interpretation: "without confirmation token" = "without user approval"; provider returning False ⇒ write rejected ✓. Not yet wired into `build_brain` / REPL — a follow-up (likely with DCL-025 tool registry).
- **DCL-021** — Tool: `filesystem_read` (workspace-scoped). `declaw/tools/builtin/filesystem.py` is the first real built-in tool: a `DeclawTool[FilesystemReadArgs]` that reads UTF-8 text files from the user's workspace. `FilesystemReadArgs` carries `path` (required, workspace-relative) and `max_bytes` (default 100000, `ge=1` to keep one tool call from blowing the context window). The hot path is `_resolve_in_workspace`: three layers of defence — absolute-path reject (no `/etc/passwd`, no `C:\…`, no UNC), `(workspace / candidate).resolve()` to canonicalise symlinks AND NTFS 8.3 short names, then `Path.relative_to(workspace)` for containment. Escape raises `WorkspacePathError(ValueError)`, which LangGraph's `ToolNode` surfaces as a `ToolMessage` the model and audit trail can see. `ToolClass.READ`, so the (eventual) confirmation queue lets it auto-run. 13 unit tests in `tests/unit/test_tools_filesystem.py`: happy path (basic, UTF-8 with French accents, nested), the traversal corpus (`..`, multi-`..`, absolute path, symlink-to-outside `pytest.skip` if symlinks aren't supported, NTFS short-name escape `skipif` Windows-only — all rejected on dev hardware), file-shape errors (missing, directory, oversize) and the pydantic schema (`max_bytes ≥ 1`, `path` required). 12 pass on Windows; symlink test skips without admin/dev-mode. `_resolve_in_workspace` is a candidate for promotion to a shared `declaw/tools/builtin/_paths.py` when DCL-022 lands a second consumer.
- **DCL-020** — `BaseTool` abstract class with typed params. `declaw/tools/base.py` defines `DeclawTool(BaseModel, Generic[ArgsT])` — a Pydantic-validated tool definition that subclasses parameterise with their concrete `args_schema` (e.g. `class EchoTool(DeclawTool[EchoArgs])`). Five fields: `name`, `description_en`, `description_fr`, `classification` (`ToolClass.READ / WRITE / DESTRUCTIVE`), `args_schema: type[ArgsT]`. The base `_arun` raises `NotImplementedError` (abstract by convention — avoids the `ABCMeta` × `ModelMetaclass` conflict). `run_validated(raw_args)` validates against the schema then calls `_arun` (raises `pydantic.ValidationError` on bad args — the acceptance: "runtime rejects invalid params"). `description_for(language)` switches EN/FR. `as_langchain_tool(language)` builds a `StructuredTool` with the locale-appropriate description so `bind_tools` sends Mistral the right language (probe data: FR implicit reliability was 0/5 with English-only descriptions — bilingual descriptions are mandatory, not optional). `frozen=True`. 11 unit tests in `tests/unit/test_tools_base.py` cover instantiation, valid/invalid args (missing required, wrong type), abstract enforcement, locale switch, the langchain adapter (description + schema + end-to-end `ainvoke` + `ValidationError` propagation), and the frozen guarantee. Real typed/validated filesystem tools land in DCL-021..026 on top of this base.

## Open decisions
- **Ollama lifecycle / end-user packaging** (raised 2026-05-27). MVP DoD requires "install in < 5 min, no terminal required" for non-technical users (lawyers, doctors). They cannot manually install Ollama, pull a model, or fix PATH — yet that is exactly the current dev setup. DeClaw must own the full Ollama lifecycle (install, start daemon, health-check, auto-pull missing model) and hide it from the user, surfacing only a "preparing AI engine…" progress UI. Options:
  - **A — Bundle Ollama** inside the Tauri installer (heavier app ~hundreds of MB, must track Ollama versions).
  - **B — Download on first run** (light installer, needs internet once for ~4GB model; must log the download to the audit trail per Principle #7 and clearly frame it as "one-time, then fully offline").
  - **C — Embed llama.cpp/llamafile directly** (drop Ollama; full control but lose Ollama's model management + API, more work).
  - End-user config (`ollama_base_url`, `model`) must default to sane values (run with zero config) and be changed only via the Phase 9 Settings UI — never via `.env`/terminal. **Likely needs a dedicated ticket** ("Ollama lifecycle management") around Phase 7 or earlier. Decision deferred — no option chosen yet.
- **Docker requirement for end-users / shell execution in MVP** (raised 2026-05-27). Per Principle #3, Docker is mandatory *only for shell execution* — "disabled, not bypassed" when absent. So Docker's absence must **disable the shell tool, not block the app**. Key realization: **the v0.1 MVP feature set does not need shell execution.** The 5 DoD items (read PDF/DOCX/XLSX, cited Q&A, move/rename/summarize via NL, audit log, egress monitor) all work without a shell — file move/rename runs through the os-bridge plugin with **typed, validated parameters** (Principle #6) via Python `shutil`, not shell commands. Meanwhile Docker Desktop is a *heavier* burden on non-technical users than Ollama: (a) needs WSL2 + BIOS virtualization + admin rights, which lawyers/doctors typically can't set up; (b) **Docker Desktop licensing is paid** for orgs >250 employees OR >$10M revenue — law firms / medical practices may fall under this, a real cost/legal risk; (c) multi-GB RAM footprint. Options:
  - **A — Drop shell execution from v0.1** (recommended leaning): no Docker dependency at all for MVP → lightweight install, matches "< 5 min, no terminal". Shell + sandbox deferred to post-MVP.
  - **B — Keep shell in v0.1** but solve the sandbox-for-non-technical-user problem without forcing Docker Desktop: candidates are Windows Sandbox (Win Pro built-in), WSL2 directly (avoids Desktop licensing), gVisor/Firecracker/nsjail (Linux-first), or bundling Docker Engine (not Desktop).
  - Two follow-ups regardless of choice: (1) the **end-user runtime startup** must treat a failed Docker check as "disable shell tool + warn", unlike the current dev `scripts/preflight.py` which exits 1 — `declaw/preflight.py` does not yet distinguish these two modes. (2) **Phase-gating impact**: Phase 3 (sandbox) is currently a gate for Phase 9 (Web UI); if shell is deferred, Phase 3 may drop off the MVP critical path (Phase 4 sanitizer remains the real gate) — revisit gating separately. Decision deferred — no option chosen yet.
- **Proactive "heartbeat" agent loop (OpenClaw-style)** (raised 2026-05-28). OpenClaw (Peter Steinberger's self-hosted local AI assistant — close in philosophy to DeClaw) has a *heartbeat*: on a fixed interval (~30 min) the system wakes the agent, which reads a `HEARTBEAT.md`, performs configured checks (email, calendar, metrics), and either reports or stays silent (`HEARTBEAT_OK`, <1k tokens). This turns a **reactive** agent (waits for commands) into a **proactive** one (acts on a schedule). DeClaw is currently reactive-only, but the roadmap already has the foundation: **APScheduler** (listed under Future ideas, Phase 2 / post-MVP). Reasoning on whether DeClaw should adopt this:
  - **For**: genuinely useful for the target professionals (watch a folder for new docs, remind about deadlines, summarize newly-arrived email); a differentiator vs purely reactive assistants; scheduler infra already planned.
  - **Against (tensions with DeClaw's DNA)**: (1) conflicts with the **confirmation-required** model (MVP DoD #4) — who confirms an autonomous action when the user is away? (2) **legal-liability risk** for regulated professionals — an agent auto-acting on privileged email without supervision is dangerous; (3) **privacy/audit** — scheduled access to email/calendar even when the user is absent must be fully local + logged (Principles #5, #7); (4) **LLM reliability** — DeClaw runs local Mistral 7B, far weaker than the cloud models OpenClaw likely assumes; autonomous decisions on a 7B model are risky; (5) cost is compute/electricity on the user's machine (not API $, since Ollama is local).
  - **Leaning**: keep DeClaw **reactive for v0.1**; treat proactive heartbeat as **post-MVP**, built on APScheduler. Even then, default to **"observe + notify"** (watch and surface findings), **not "act autonomously"** — any action still routes through the confirmation queue + audit trail. Decision deferred — no option chosen yet.
- **build_brain ↔ registry wiring + production confirmation provider** (raised 2026-06-10, after DCL-025). The tool layer is complete and `registry.langchain_tools(language, approve)` produces the brain-ready list, but `build_brain` still defaults to the `echo` stub — the real filesystem tools are not in `declaw chat` yet. Wiring them needs a **production `ConfirmationProvider`** that asks the human, and in the REPL that means a blocking `console.input("Allow filesystem_write(...)? [y/N] ")` called from inside an **async `ToolNode`** — which must be offloaded via `asyncio.to_thread` (or an injected prompt callback) so it doesn't stall the event loop. This is a real async-UX design (how to render the pending call, default-deny on EOF/Ctrl-C, audit the decision per Principle #7), not just plumbing, so it was deliberately deferred out of DCL-025. Likely a dedicated ticket ("wire tools into the REPL with confirmation") before or alongside Phase 8 (doc-intel) where these tools are first user-visible. The gateway (Phase 9) will need its own provider (a UI prompt over WebSocket), so the provider abstraction must stay transport-agnostic. Decision: do this as a focused follow-up; not yet scheduled.
- **User-behavior / preference memory gap** (raised 2026-05-28). Standard agent-memory taxonomy has 4 types: short-term (working/conversation buffer), semantic (facts + **user-specific** preferences/profile/prior decisions), episodic (timestamped log of past interactions), procedural (learned how-to/workflows). DeClaw's Phase 5 covers: DCL-052 short-term buffer ✓, DCL-053 semantic (but scoped "vector search by **topic**" — document-oriented, NOT user preferences), DCL-054 episodic (task history), DCL-055 retrieval-into-context. **Gap**: no ticket builds a *user-preference / behavioral* memory layer (preferred language, answer style, frequent folders/actions), and **no procedural memory** ticket at all. So DeClaw has the infrastructure (ChromaDB + nomic-embed-text + episodic store) to remember user behavior, but the current plan does not explicitly *learn* preferences to improve UX. Notably DeClaw is **well-positioned to do this ethically** vs cloud assistants: 100% local, Fernet at-rest (DCL-051), GDPR export (DCL-056) + wipe (DCL-057), audit trail — could be a privacy-first differentiator ("learns your habits, 100% on-device, erasable anytime"). Caveats: for regulated professionals this is sensitive profiling → must be **opt-in + transparent + wipe-able**; procedural automation must still route actions through confirmation (same tension as the heartbeat decision). Possible follow-up tickets (Phase 5 or post-MVP): (1) "User preference memory" — a semantic sub-collection for stable profile facts; (2) "Procedural memory" (post-MVP) — learn repeated workflows. Decision deferred — no ticket added yet.
